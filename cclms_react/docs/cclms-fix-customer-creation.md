CCLMS Customer Management -- Supabase Connection and Fix Documentation

1. Overview

The CCLMS Customer Management module connects the React Vite frontend to
Supabase.

The module allows the store owner to:

View customers

Add customers

Edit customers

Delete customers

View each customer's generated customer ID

Keep customers separated by store

The system uses the authenticated owner's Supabase account to determine
which store the owner belongs to.

3. Owner and Store Identification

The owner account is identified by the Supabase Auth UUID.

For example:

Owner/Profile ID:
d15e9d85-86f3-4ba0-a72a-858b1d60d7e1

The owner's store has its own UUID:

Store ID:
e5ad8670-ad89-4322-9516-fbfe4eb67235

The relationship is:

Owner
d15e9d85-86f3-4ba0-a72a-858b1d60d7e1
        |
        | profile_id
        v
Store
e5ad8670-ad89-4322-9516-fbfe4eb67235
        |
        | store_id
        v
Customers

Important

For customer ownership, CCLMS uses:

customers.store_id

instead of placing an owner_id directly on every customer.

This allows the application to determine ownership through the owner's
store.

4. Getting the Current Owner's Store

The application uses the logged-in Supabase user:

const {
  data: { user },
  error,
} = await supabase.auth.getUser()

The user's ID is then used to find the owner's store:

const { data, error } = await supabase
  .from("store_owners")
  .select("id")
  .eq("profile_id", user.id)
  .single()

The returned id is the store ID.

Conceptually:

auth.uid()
    ↓
store_owners.profile_id
    ↓
store_owners.id

5. Store Owner RLS Problem and Fix

Initially, the store_owners table had only this type of policy:

Admins can view store owners

That policy allowed admins to read store owners, but not owners.

The owner application therefore received:

406 Not Acceptable

when trying to read:

store_owners

Fix

An owner SELECT policy was added:

CREATE POLICY "Owners can view own store"
ON public.store_owners
FOR SELECT
TO authenticated
USING (
    profile_id = auth.uid()
);

This allows an owner to read only their own store record.

It does not allow one owner to read another owner's store.

7. Random Customer ID Generation

Customer IDs are generated by PostgreSQL.

Example:

CUST-A7K29P
CUST-81FD20
CUST-B93K1A

The frontend does not create the customer ID.

The database function is:

CREATE OR REPLACE FUNCTION public.generate_customer_code()
RETURNS text
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
    new_code text;
BEGIN
    LOOP
        new_code :=
            'CUST-' ||
            upper(
                substr(
                    md5(random()::text || clock_timestamp()::text),
                    1,
                    6
                )
            );

        IF NOT EXISTS (
            SELECT 1
            FROM public.customers
            WHERE customer_code = new_code
        ) THEN
            RETURN new_code;
        END IF;
    END LOOP;
END;
$$;

The column uses the function as its default:

ALTER TABLE public.customers
ALTER COLUMN customer_code
SET DEFAULT public.generate_customer_code();

The customer ID is also protected by a unique constraint:

ALTER TABLE public.customers
ADD CONSTRAINT customers_customer_code_unique
UNIQUE (customer_code);

This gives two levels of protection:

The generator checks whether the ID already exists.

The database UNIQUE constraint prevents duplicates.

8. Customer Creation Flow

The correct customer creation flow is:

Owner opens Add Customer
        ↓
React form opens
        ↓
Owner enters customer information
        ↓
React calls createCustomer()
        ↓
getCurrentStoreId()
        ↓
Supabase INSERT
        ↓
PostgreSQL generates customer_code
        ↓
CUST-XXXXXX
        ↓
Customer is returned to React
        ↓
Customer list refreshes

The INSERT should not manually provide customer_code.

Example:

const storeId = await getCurrentStoreId()

const {
  data,
  error,
} = await supabase
  .from("customers")
  .insert({
    store_id: storeId,
    name: input.name,
    phone_number: input.phoneNumber || null,
    address: input.address || null,
    status: "active",
  })
  .select("id, customer_code")
  .single()

The important part is:

customer_code

is not included in the INSERT.

PostgreSQL creates it automatically.

9. Old Customer ID Generation

The old implementation used a frontend function similar to:

ownerApi.nextCustomerCode()

This was not needed for the new database-generated ID system.

The old approach attempted to generate customer IDs before saving the
customer.

The new approach is:

Frontend
   ↓
Create customer
   ↓
Database generates ID

Therefore, the Add Customer dialog should not call:

ownerApi.nextCustomerCode()

The correct function is:

function openAddDialog() {
    setEditingCustomer(null)

    reset({
        customerCode: "",
        name: "",
        phoneNumber: "",
        address: "",
    })

    setDialogOpen(true)
}

The ID can remain blank in the Add Customer form because it is generated
when the record is saved.

11. Customer RLS Policies

The final customer RLS policies are:

owner can read own customers
owner can insert own customers
owner can update own customers
owner can delete own customers

They enforce:

SELECT

store_id = current_owner_store_id()

INSERT

store_id = current_owner_store_id()

UPDATE

store_id = current_owner_store_id()

DELETE

store_id = current_owner_store_id()

The policies prevent an owner from accessing another owner's customers.

12. current_owner_store_id()

The function used by the customer RLS policies is:

CREATE OR REPLACE FUNCTION public.current_owner_store_id()
RETURNS uuid
LANGUAGE sql
STABLE
SECURITY DEFINER
SET search_path = public
AS $$
    SELECT so.id
    FROM public.store_owners AS so
    JOIN public.profiles AS p
        ON p.id = so.profile_id
    WHERE so.profile_id = auth.uid()
      AND p.role = 'owner'
    LIMIT 1;
$$;

It performs:

auth.uid()
    ↓
store_owners.profile_id
    ↓
profiles.role = owner
    ↓
store_owners.id

The returned store ID is then compared with:

customers.store_id

13. SQL Permissions

RLS alone is not enough.

PostgreSQL also requires the authenticated role to have table
permissions.

The following customer permissions were required:

GRANT SELECT, INSERT, UPDATE, DELETE
ON TABLE public.customers
TO authenticated;

This means:

SELECT  → View customers
INSERT  → Add customers
UPDATE  → Edit customers
DELETE  → Delete customers

RLS still controls which rows the owner can access.

14. owner_customer_balances View

After creating a customer, the API reads:

owner_customer_balances

The API uses the view to return the customer's balance information.

The authenticated role therefore needs SELECT permission:

GRANT SELECT
ON TABLE public.owner_customer_balances
TO authenticated;

The view depends on other tables.

During troubleshooting, PostgreSQL reported missing permissions for:

credit_entries
payments

The required permissions were:

GRANT SELECT
ON TABLE public.credit_entries
TO authenticated;

and:

GRANT SELECT
ON TABLE public.payments
TO authenticated;

This allowed the balance view to access its required data.

15. Difference Between PostgreSQL Permissions and RLS

These are two different security layers.

PostgreSQL permissions

Example:

GRANT SELECT, INSERT
ON public.customers
TO authenticated;

This answers:

Is this role allowed to access the table?

RLS

Example:

USING (
    store_id = public.current_owner_store_id()
)

This answers:

Which rows is this authenticated user allowed to access?

The system needs both.

Authenticated role
       ↓
Table permission
       ↓
RLS policy
       ↓
Allowed rows

16. Errors Encountered and Fixes

Error 1: 406 Not Acceptable

Request:

/rest/v1/store_owners?select=id&profile_id=eq.<owner-id>

Cause:

The owner did not have permission to SELECT their own store_owners
row.

Fix:

CREATE POLICY "Owners can view own store"
ON public.store_owners
FOR SELECT
TO authenticated
USING (
    profile_id = auth.uid()
);

Error 2: 403 permission denied for table customers

Error:

code: 42501
message: permission denied for table customers

Fix:

GRANT SELECT, INSERT, UPDATE, DELETE
ON TABLE public.customers
TO authenticated;

Fix:

GRANT SELECT
ON TABLE public.owner_customer_balances
TO authenticated;

Error 4: permission denied for table credit_entries

Fix:

GRANT SELECT
ON TABLE public.credit_entries
TO authenticated;

Fix:

18. Security Model

The owner should only access records belonging to their store.

The important rule is:

customers.store_id
=
current_owner_store_id()

This prevents an owner from simply changing a customer record's
store_id to access another store.

The INSERT policy also checks the store:

WITH CHECK (
    store_id = public.current_owner_store_id()
)

The UPDATE policy checks both the existing and new row:

USING (
    store_id = public.current_owner_store_id()
)
WITH CHECK (
    store_id = public.current_owner_store_id()
)
