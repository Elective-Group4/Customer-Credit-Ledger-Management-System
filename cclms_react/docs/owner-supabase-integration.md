# Store Owner Supabase Integration

This document explains how the Store Owner UI connects to the real Supabase database.

The application uses this flow:

```text
React page
  -> owner hook
  -> src/lib/api/owner.js
  -> Supabase JS client
  -> Postgres table, view, or RPC
  -> mapped JavaScript data returned to the UI
```

The UI does not query Supabase directly. All owner business-data requests go through [owner.js](../src/lib/api/owner.js).

## Client Configuration

The shared Supabase client is defined in [supabase.js](../src/lib/supabase.js):

```env
VITE_SUPABASE_URL=your-supabase-project-url
VITE_SUPABASE_PUBLISHABLE_KEY=your-supabase-publishable-key
```

Only the publishable/anonymous browser key belongs in the Vite frontend. A Supabase service-role key must never be placed in React code or a `VITE_*` variable.

## Store Scoping

Before owner-created records are inserted, `ownerApi` calls `getCurrentStoreId()`:

1. `supabase.auth.getUser()` retrieves the authenticated user.
2. `store_owners` is queried using `profile_id = user.id`.
3. The resulting `store_owners.id` becomes `store_id` for inserts.
4. Supabase RLS must enforce the same ownership boundary for reads, updates, and deletes.

If there is no authenticated user or no matching `store_owners` row, the API throws an error and the page displays its error state/toast.

## Product Management

Page:

- [ProductManagement.jsx](../src/components/Modules/StoreOwner/ProductManagement.jsx)
- [use-owner-products.js](../src/hooks/use-owner-products.js)

API calls:

| UI action      | API method                          | Supabase operation                                             |
| -------------- | ----------------------------------- | -------------------------------------------------------------- |
| Load products  | `ownerApi.listProducts()`           | `products.select('*').order('name')`                           |
| Add product    | `ownerApi.createProduct(input)`     | Insert into `products` with the authenticated owner `store_id` |
| Edit product   | `ownerApi.updateProduct(id, input)` | Update `name`, `id_code`, `price`, and `updated_at`            |
| Delete product | `ownerApi.deleteProduct(id)`        | Delete by product ID; RLS limits access                        |
| Toggle status  | `ownerApi.toggleProductStatus(id)`  | Read current status, then update to `active` or `inactive`     |

The API maps database columns to UI names:

```text
id_code -> idCode
created_at -> createdAt
updated_at -> updatedAt
price -> number
```

After every successful mutation, the product hook reloads the list. Errors are caught by the component and shown through Sonner.

## Customer Management

Page:

- [CustomerManagement.jsx](../src/components/Modules/StoreOwner/CustomerManagement.jsx)
- [use-owner-customers.js](../src/hooks/use-owner-customers.js)

API calls:

| UI action       | API method                           | Supabase operation                                                           |
| --------------- | ------------------------------------ | ---------------------------------------------------------------------------- |
| Load customers  | `ownerApi.listCustomers()`           | Select from `owner_customer_balances`                                        |
| Add customer    | `ownerApi.createCustomer(input)`     | Inserts customer details without `customer_code`                             |
| Edit customer   | `ownerApi.updateCustomer(id, input)` | Updates name, phone, address, and timestamp                                  |
| Delete customer | `ownerApi.deleteCustomer(id)`        | Calls `delete_customer_if_settled`; soft-deletes only zero-balance customers |

The customer code is generated by the database default. React does not insert or preview the final code. The add dialog leaves the ID blank and displays `Generated on save`; the returned row is visible after the customer list refreshes.

The customer balance is read from `owner_customer_balances`, not calculated in React.

Deletion is allowed only at a zero balance; active/inactive status does not affect eligibility. It preserves credit and payment history by setting `customers.deleted_at`. The balance view excludes those rows. Positive and negative balances are rejected by the database RPC with the settle-balance message. The RPC also records a customer-name/code snapshot in `customer_deletion_events` for Transaction History.

Run `supabase/account-theme-and-ledger-security.sql` in the Supabase SQL Editor to create the deletion-event table, owner-scoped read policy, and updated deletion RPC.

The API maps:

```text
customer_code -> customerCode
phone_number -> phoneNumber
created_at -> createdAt
balance -> number
```

## Credit / Utang

Page:

- [CreditTab.jsx](../src/components/Modules/StoreOwner/CreditTab.jsx)
- [use-owner-credits.js](../src/hooks/use-owner-credits.js)

Initial loading requests all related data:

```text
ownerApi.listCustomers()
ownerApi.listProducts()
ownerApi.listCredits()
ownerApi.listPayments()
```

Credit loading reads `credit_entries` with:

- The related customer name from `customers`
- Related rows from `credit_entry_items`

The API maps database fields such as:

```text
customer_id -> customerId
total_amount -> totalAmount
due_date -> dueDate
created_at -> createdAt
credit_entry_items -> items
```

### Creating Credit

The Add Credit form calls:

```text
ownerApi.createCredit({
  customerId,
  productId,
  quantity,
  dueDate
})
```

The API calls the existing RPC:

```text
create_credit_entry
```

RPC parameters:

```text
p_customer_id
p_product_id
p_quantity
p_due_date
```

The RPC must atomically create:

1. A `credit_entries` row
2. A `credit_entry_items` row
3. The calculated total using the product price
4. The authenticated owner `store_id`

Only active customers can receive new credit. The credit form filters inactive customers and the database trigger installed by `account-theme-and-ledger-security.sql` rejects direct inserts for inactive or deleted customers. Payments remain available for existing inactive customers.

### Payments

The customer ledger dialog calls:

```text
ownerApi.createPayment({
  customerId,
  amount,
  paymentType
})
```

The API calls the existing RPC:

```text
create_payment
```

RPC parameters:

```text
p_customer_id
p_amount
p_payment_type
```

The RPC must validate the current balance and reject payments greater than the outstanding amount. The resulting Supabase error is caught and shown to the owner.

Payment history is loaded with:

```text
ownerApi.listPayments()
```

After a successful payment, the credit hook reloads customers, credits, products, and payments, so the displayed balance and payment history update together.

## Owner Dashboard

Page:

- [OwnerDashboard.jsx](../src/components/Modules/StoreOwner/OwnerDashboard.jsx)
- [use-owner-dashboard.js](../src/hooks/use-owner-dashboard.js)

The dashboard calls:

```text
ownerApi.getDashboard()
```

That method runs these RPCs in parallel:

```text
owner_dashboard_totals
owner_credit_ranking
owner_monthly_credit_summary
```

The API normalizes the RPC response into the shape already used by the dashboard:

```text
totals.totalCustomers
totals.overallBalance
totals.activeCustomers
totals.customersDueThisMonth
ranking[]
monthlyCredit[]
```

The charts use only returned database values:

- Customer Status pie chart uses active and inactive customer totals.
- Credit by Month bar chart uses monthly credit and payment totals.
- Credit Ranking uses the ranking RPC ordered by outstanding balance.

No chart values are generated in the component.

## Transaction History

Page:

- [TransactionHistory.jsx](../src/components/Modules/StoreOwner/TransactionHistory.jsx)
- [use-owner-transactions.js](../src/hooks/use-owner-transactions.js)

The page calls:

```text
ownerApi.listTransactions()
```

The API reads `credit_entries` with:

- The related customer name
- Related `credit_entry_items`

It also reads owner-scoped `customer_deletion_events` and merges those audit events into the chronological list. Deletion entries show the deleted customer name and code without removing their financial history.

It maps each row to:

```text
id
customerId
customerName
products
createdAt
```

The page applies search and date filtering to the returned data, then paginates the filtered list at 10 rows per page.

Excel export uses the entire filtered list, not only the current page.

## Loading and Error Handling

Each Owner page uses a dedicated hook with these states:

```text
loading
error
data
refresh()
```

The normal flow is:

1. Set loading to true.
2. Clear the previous error.
3. Call `ownerApi`.
4. Store returned data.
5. Render empty state when the result is empty.
6. Render an error state when Supabase returns an error.
7. Set loading to false.

Mutations also:

- Use `try/catch`.
- Show a success toast after completion.
- Show an error toast when Supabase rejects the request.
- Refresh the relevant page data afterward.

## Security Requirements

The frontend uses only the publishable Supabase client. Security must be enforced by Supabase:

- Keep RLS enabled on `products`, `customers`, `credit_entries`, `credit_entry_items`, and `payments`.
- Scope rows to the authenticated owner’s `store_owners.id`.
- Do not trust a client-provided `store_id`.
- Do not expose the service-role key.
- Use RPCs for credit and payment operations so validation and writes are atomic.
- Ensure child records cannot be inserted for another owner’s parent records.

The application’s role guard protects `/owner`, but the database RLS policies are still required because route guards alone are not database security.

## Owner Profile and Theme

The Owner Profile feature uses Supabase Auth and the `profiles` table through `src/lib/api/profile.js`. The application stores each authenticated user's theme in `profiles.theme_preference` through the `set_my_theme_preference` RPC. The browser also uses a user-specific `next-themes` storage key, so switching accounts does not carry over the previous account's theme.
